# Docker

Run PiPulse in Docker on a 64-bit host. For a native install see [Install](install.md); for the certificate see [HTTPS](https.md).

**Docker** (64-bit hosts: a Pi 3/4/5 on 64-bit Pi OS, or a PC): download [`compose.yaml`](../compose.yaml), put your settings in `pipulse.env` and any files in `config/` next to it, then `docker compose up -d`. It runs three services. `pipulse-tls-init` is a one-shot that sets the owners and modes of two volumes (the only service with a capability, `CHOWN`). `pipulse-tls` is a sidecar that holds the CA key in its own `tls-ca` volume, makes the certificate and renews it every 6 hours. `pipulse` is the server: read-only, no capabilities, and it mounts only the certificate (`/tls`, read-only) and never the CA key. The server waits for the sidecar to be ready, but a failed renewal does not keep it from starting: that shows in `docker compose logs pipulse-tls`, `pipulse tls status` and `/api/health`. To use your own certificate instead, put the files in `config/` (the server sees them at `/etc/pipulse`), set `PIPULSE_TLS_CERT`, `PIPULSE_TLS_KEY` and, for a private CA, `PIPULSE_TLS_CA` in `pipulse.env`, and make the key readable by the container's `pipulse` user only: `sudo chown 999:999 config/<key> && sudo chmod 600 config/<key>` (a key readable by everyone is refused). No CA is made then, and the sidecar just stays idle.

- **The fingerprint:** `docker compose logs pipulse-tls` prints the CA fingerprint and what it covers on every start. Check it before you trust the CA, then `docker compose exec pipulse pipulse tls export-ca`.
- **Cover an IP range:** `docker compose run --rm pipulse-tls pipulse tls new-ca --subnet 192.168.1.0/24 --yes` (a container can't ask your terminal for confirmation, so `--yes` is the consent; the same consequence text applies), then `docker compose restart pipulse`. A fresh volume covers names only; `PIPULSE_TLS_SUBNETS` in `pipulse.env` sets ranges for the first start.
- **The sidecar shares the host network** (to see the host name and default-route address) and opens no sockets; that is a code-level guarantee (a test keeps network modules out of it), not a container boundary.
- **Clock:** the compose file mounts `/run/systemd/timesync` so certificates are only issued on a synchronized clock. On a chrony or ntpd host, delete that mount (twice in the file) and set `PIPULSE_TLS_CLOCK=trust` in `pipulse.env`.
- **An existing database counts as an upgrade:** copying an old database into a fresh setup stays on HTTP, with the line to enable HTTPS in the logs: `docker compose run --rm pipulse-tls pipulse tls enable --yes`, then `docker compose restart pipulse`. A plain `docker run` needs `PIPULSE_TLS=off` or your own certificate, and refuses to start otherwise.
- **Upgrading an existing Docker install to 0.7.0:** the image no longer starts without HTTPS set up, so pulling `:latest` and keeping the old `compose.yaml` makes the server stop at start with "no HTTPS certificate is set up" and restart in a loop (monitoring stops until you fix it). Either download the current [`compose.yaml`](../compose.yaml) (it adds the `pipulse-tls` sidecar and its volumes; your database volume is kept, so the install stays on plain HTTP until you run `docker compose run --rm pipulse-tls pipulse tls enable --yes` and `docker compose restart pipulse`), or keep the old file and add `PIPULSE_TLS=off` to its environment.
- `PIPULSE_TLS=off` in `pipulse.env` makes the sidecar make no CA and the server serve HTTP.

The compose file shares the host's network and mounts `/boot/firmware`, `/etc/os-release` and the Pi model read-only, so the readings are the host's, not the container's; core voltage and throttling need the Pi firmware and show "Not available in Docker". The server's health check (`/api/health`) shows up in Docker, Dockhand and Portainer. Keep it on your LAN.
