# PiPulse — project instructions for Claude

PiPulse is a from-scratch TypeScript rewrite of [RPi-Monitor](https://github.com/RPi-Monitor/RPi-Monitor). This file is read automatically by Claude Code (CLI) when working in this repo, so it doesn't matter whether work continues here via Claude Code or via Cowork/claude.ai — both should end up looking at the same two documents below.

## Where the plan lives

- **`README.md`** — current status, tech stack with pinned versions, getting-started commands, and the roadmap table (which phase is done, which is next).
- **`docs/PLAN.md`** — the full modernization plan: legacy architecture review, every architecture decision and why, data/storage schema, API/frontend design, deployment plan, feature-parity matrix, the phase-by-phase build plan with exit criteria, testing strategy, security considerations, and future-proofing notes. Read this before starting a new phase.

Read both before proposing what to build next — `README.md`'s roadmap table is the quick status check, `docs/PLAN.md` has the reasoning and exit criteria behind each phase.

## Current status

Phase 0 (foundations) is done: npm-workspaces monorepo (`packages/storage`, `packages/collector`, `packages/api`, `packages/web`), lint (ESLint flat config), tests (Vitest), CI (GitHub Actions, Node 22.x/24.x matrix).

Phase 1 (collector core) is done (PR #1): `packages/collector` has the versioned `CollectorPlugin` interface with runtime `validatePlugin()` checks and a contract suite run against every built-in plugin; six built-in plugins (`cpu_load`, `memory_used`, `network_rx`, `network_tx`, `disk_used`, `cpu_temperature`); `startScheduler()` (per-plugin intervals, skips a tick while the previous read is still in flight, `stop(timeoutMs)` drains before the db closes); and a `src/main.ts` daemon (`PIPULSE_DB_PATH`, clean SIGINT/SIGTERM shutdown). Exit criterion verified on the real Pi-hole Pi (armv7l): all six metrics landed at their configured 5 s / 10 s / 60 s intervals. 51 tests passing; `npm test`, `npm run build`, `npm run lint`, and `npm run format` all green.

Phase 2 (API layer) is done (PR #4): `packages/api/src/server.ts` is a single process that runs the collector scheduler and serves Fastify REST (`/api/config`, `/api/metrics/latest`, `/api/metrics/:id/history` with schema-validated `from`/`to`) plus a `/api/live` WebSocket (`snapshot` on connect, then one `sample` per reading). The scheduler's `onSample` hook publishes into an in-process `LiveFeed` (a small interface in `packages/api`, so the API never imports the scheduler directly). Config via `PIPULSE_DB_PATH`, `PIPULSE_HOST`, `PIPULSE_PORT`. Exit criterion verified from a Mac against the Pi on port 8889: `curl` and a WebSocket client both returned live data. 65 tests passing.

Phase 3 (dashboard) is done (PRs #6, #7): `packages/web` is a Preact dashboard served by the API at `/` (`@fastify/static`, `PIPULSE_WEB_DIR`). Hostname header with model/OS/kernel from `/api/config`'s `device` section and uptime from its top-level `uptimeMs` (read from `os.uptime()` on every request and advanced in the browser with `performance.now()`; deliberately not a stored boot timestamp, because the Pi has no RTC and a boot time computed before NTP syncs stays wrong by however far the clock later jumps), a Live/Reconnecting indicator that pulses per sample, and one tile per plugin (formatted value, meter where there's a ceiling, 15-minute sparkline from history + live samples). Display-only status thresholds (icon + words, never colour alone) live in `packages/web/src/status.ts` until Phase 5's alert engine. Staleness and history windows use the Pi's clock (`serverTime`, then pushed sample timestamps). 11 built-in plugins now, including `swap_used`, `boot_used`, `cpu_frequency`, and `cpu_voltage`/`throttled` via `vcgencmd` (the vcgencmd plugin deferred from Phase 1). Exit criterion verified by screenshot side by side with RPi-Monitor's `status.html` on the Pi: PiPulse shows everything that page does except load averages and cumulative network totals, deferred to Phase 4. 183 tests passing.

Phase 4 (history & charts) is done (PR #14): a housekeeping job (`startHousekeeping` in `packages/storage/src/rollup.ts`, run in-process every minute) rolls raw → 1m → 1h → 1d and prunes per `PIPULSE_RETENTION_*` (defaults raw 2d, 1m 14d, 1h 1y, 1d forever). Daily buckets are the server's **local** calendar days (DST-aware, built from 1m rollups), with a `rollup_progress` table (migration 3) recording where they stopped. `GET /api/metrics/:id/series` returns avg/min/max points; `resolution=auto` (`chooseResolution`) picks the finest level that is whole across the window (not yet pruned there by retention) and actually holds ≤1500 rows for that metric in it — counted with a `LIMIT 1501` index scan, not estimated from the span, so a database younger than a level's first bucket (e.g. <1 h for hourly) still gets the readings it has instead of an empty chart. `packages/web` has a hash-routed History page (`#/history?range=1h|6h|24h|7d|30d|1y`) with uPlot charts, drag-to-zoom (refetches finer data), a low–high band and gap breaks. Exit criterion verified on the Pi 2 with a seeded year-equivalent database (380k raw / 222k 1m / 96k 1h / 4k 1d rows): every range answers in under 75 ms, the 1-year page loads all ten series in ~250 ms from daily rows, and series queries seek on the primary key (no raw-table scan). 273 tests passing.

Phase 5a (alerting) is done (PR #18): `packages/alerts` holds the rules (built-ins in `rules.ts`, merged by `id` with the operator's `PIPULSE_ALERTS_FILE`; one condition per rule — `atLeast`/`atMost`/`bitsSet`/`noReadingFor` — with `for`/`clearAfter` durations; an invalid file stops startup), a pure raise/clear decision over covered windows of readings (`evaluate.ts`), a SQLite adapter (`store.ts`, the `alerts` table is migration 4) and a 15 s engine run in the server that survives restarts and clock jumps and logs a failed check instead of crashing. The API serves `GET /api/alerts`, `rules` in `/api/config`, open `alerts` in the WebSocket snapshot and an `alert` message per raise/clear. The dashboard colours tiles from the same rules (replacing the display-only thresholds), shows open alerts live on tiles, and has an Alerts page (open, last 30 days, rules in force) with a per-severity badge in the nav. A window only counts as evidence if readings reach both ends and no more than two polls are missed in a row anywhere in it; silence rules fall back to the newest rollup bucket once the raw reading is pruned, so `noReadingFor` isn't bound by raw retention. Exit criterion verified on the Pi 2 (port 8889, test rules file): a `yes`-loop CPU breach opened `test_busy` live on the Alerts page and badge with no reload, the same alert (one row) survived a server restart, it cleared ~1 min after `pkill yes` (`clearedBy: condition`) and moved to Recent live, a 30 s `noReadingFor` rule on the 60 s `disk_used` opened and cleared every minute, `/api/alerts` answered in 26–40 ms, and no `alert rule … failed` lines were logged. 381 tests passing.

Phase 5b-1 (sign-in, settings, retention editor) is done (spec `docs/superpowers/specs/2026-09-23-settings-auth-design.md`, plan `docs/superpowers/plans/2026-09-23-settings-auth.md`). `packages/api/src/auth.ts` (no Fastify types) holds the scrypt hash file (`PIPULSE_ADMIN_PASSWORD_HASH_FILE`, made by `node packages/api/dist/hash-password.js`; unset = read-only), in-memory sessions (`pipulse_session` cookie, `HttpOnly`, `SameSite=Strict`, 7 days from last use) and the sign-in limit (5 failures per IP per 15 min). One `onRequest` hook in `auth-routes.ts` decides every request: writes need a session (and a same-host `Origin`), reads only with `PIPULSE_PROTECT_READS=true` (the WebSocket then closes with `4401`). Storage has the `settings` table (migration 5) and `retentionSource()`: environment › saved › default, re-read on every housekeeping run and `/series` request, so a saved change applies within a minute without a restart; `validateRetention` keeps levels in order and raw retention ≥ the longest alert look-back. `PUT /api/settings` answers `409` until a deleting change is confirmed; housekeeping runs `VACUUM` after large deletes (≥ 25 % free of a > 8 MB file, disk room for a copy, at most daily). The dashboard has a Settings page (preview, confirm checkbox, locked env fields, storage figures), a sign-in form, a full-page sign-in gate under read protection, and Sign out. The auth hook decides on the matched route (never the raw URL, which percent-encoding or an absolute-form target can disguise), and a preview counts only rows the change itself deletes. Exit criterion verified on the Pi 2 (port 8889, a seeded 21.6 MB database with two days of raw readings): without a hash file the Settings page was read-only and `PUT /api/settings` (and `/%61pi/settings`) answered `403`; with one, unauthenticated writes answered `401`, the `hash-password` prompt hid the typing, and cutting raw retention from `2d` to `1h` in the browser (preview, confirm, Save) deleted ~220k raw rows within a minute and logged `vacuum: 21.6 MB → 4.0 MB in 1.2 s` (requests waited a few seconds during the delete and vacuum); the saved value survived a restart, which signed the browser out; with `PIPULSE_PROTECT_READS=true` every `/api` read answered `401`, the WebSocket closed with `4401`, a signed-out browser saw only the sign-in form, and after signing in the dashboard went Live. 481 tests passing.

Phase 5b-2 (alert rules in the browser) is done (PR #20; spec `docs/superpowers/specs/2026-09-24-alert-rules-editor-design.md`, plan `docs/superpowers/plans/2026-09-24-alert-rules-editor.md`). Rules come from three layers merged by `id` — built-ins, `PIPULSE_ALERTS_FILE`, then rules saved from the browser (settings key `alerts.rules`) — via `createRuleSource()` in `packages/alerts/src/source.ts`, read live on every 15 s check. Only rules in force must fit raw retention, checked whenever something puts a rule into force (save, Enable, Revert) and at startup, where only file/built-in rules in force count, so nothing saved from the browser can stop startup; disabled rules get only a structural check, and editing a disabled rule keeps it disabled. The engine closes an alert as `rule_removed` when its rule is removed or disabled and as `rule_changed` when the rule's fingerprint (`rule_hash`) changed, re-raising at once if the edited rule still holds. Migration 6 adds `alerts.acknowledged_at` and `alerts.rule_hash`; an acknowledged alert stays open but leaves the nav badge until it clears. API: `GET /api/alerts/rules`, `POST /api/alerts/rules` (create; `409` if the id is taken), `PUT`/`DELETE /api/alerts/rules/:id`, `POST /api/alerts/:id/acknowledge`; `/api/live` sends `rules` after an edit (and in its snapshot) and `acknowledged` after an acknowledgement. The Alerts page has the rules editor (Edit / Disable / Enable / Revert / Delete, inline form with server errors under their fields) and Acknowledge buttons. `swap_heavy` now watches a `swap_io` plugin (pages/s swapped in+out from `/proc/vmstat`, History only) at ≥ 250 pages/s for 10 min instead of swap fullness; `swap_full` still watches `swap_used` ≥ 95 %. Exit criterion run on the Pi 2 (port 8889, fresh database, no rules file): a rule added in the browser opened under a `yes` load without a restart, editing it to critical closed it as `rule_changed` and reopened it critical, acknowledging dropped the badge in a second tab, disable/enable/revert applied live, and `swap_io` read 0.2 pages/s with `swap_heavy` closed. 565 tests passing.

Phase 6b-1 (TLS core) is done (PR #35, released as v0.6.3 on 2026-09-30). `packages/tls` reads the settings (`PIPULSE_TLS`, `_CERT`/`_KEY`/`_CA`, `_NAMES`, `_REQUIRE_VALID_CERT`, `_HSTS`, `_CLOCK`, `_TIMESYNC_DIR`; release default HTTP), loads and classifies an operator certificate (refused cases stop startup with one line naming the setting, e.g. `PIPULSE_TLS_CERT/PIPULSE_TLS_KEY: …` or `PIPULSE_TLS_CA: certificate N can't be parsed`; incomplete chain, untrusted top or a missing name only degrade; `notBefore`/`notAfter` are the served chain's window, so an expired intermediate reads as `expired`, never a refusal by itself), checks the clock, and reloads changed files every 60 s after two stable polls (signature includes mode/owner, context fingerprint covers key + chain), keeping the old context on a bad or worse replacement and holding replacements to startup's validity rules; a refused replacement is retried every 10 min while its files stay the same, and the reloader takes the file signature read before the startup load. `PIPULSE_TLS_NAMES` is checked against SANs only, never the subject CN. `/api/health` reports `monitoring`, `transport`, top-level `reasons` and `certificate` (enums only; an HTTP install with a password now says `degraded`/`http-with-sign-in`, release-noted); `/api/config` has `tls`; Settings has a Certificate section. One shared client check (`packages/tls/dist/health-check.js`) serves the installer and Docker `HEALTHCHECK`, trusting `PIPULSE_TLS_CA` alone when set (else Node's bundled roots) and never disabling verification; the installer runs it under `env -i` with only the settings it reads, prints its reason, and never rolls back on a verification failure (exit 2). Exit criterion verified on `Io` on 2026-09-30 with a `0.6.3-rc1` tarball from the branch (`install.sh --from`) and a throwaway test CA (names `io`, `io.lan`, `io.local`, `192.168.1.35`): HTTPS on 8889 verified from the Mac, dashboard Live in Safari over `wss://`, `pipulse_session` Secure/HttpOnly/SameSite=Strict, plain HTTP to the port dropped; an atomic replacement (key moved in before its certificate) went live in ~2 min with no restart and the tab stayed Live; a mismatched key and a leaf without its intermediate were both refused and shown on Settings while the old certificate kept serving; an expired pair started with the `SEVERE` line, `/api/health` `200 degraded` `["expired"]` and readings kept arriving, and with `PIPULSE_TLS_REQUIRE_VALID_CERT=true` it stopped with one line; the installer reported `running` over verified TLS, and without `PIPULSE_TLS_CA` (`UNABLE_TO_GET_ISSUER_CERT_LOCALLY`) or with a no-serverAuth certificate (`INVALID_PURPOSE`) warned with the reason and kept the new version. Evidence in `~/Repositories/tarballs/PiPulse/6b1-exit/`. Io was left on 0.6.3-rc1 over plain HTTP with an admin password. Phase 6b-2 (generated trust, HTTPS by default) is **planned; 6b-2a is built (next paragraphs), 6b-2b and 6b-2c are not started** (plan `docs/superpowers/plans/2026-09-30-https-6b2.md`, written on Opus 2026-09-30, revised after two reviews: the operator's review fixed CA metadata vs the served certificate's fingerprint, metadata read errors that must be visible, and the native TLS directory that must be the default; the second review's 11 blockers are folded in). Goal: every fresh install serves HTTPS from a per-install, name-constrained CA whose fingerprint the operator checks out of band and trusts once; the leaf renews itself; existing HTTP installs stay on HTTP until `sudo pipulse tls enable`. Three PRs, each leaves `main` releasable and ends with its own exit-criterion task on `Io`:

- **6b-2a** (Tasks 1–13, `release:patch` → v0.6.4), opt-in: `openssl` issuance via `execFile` (`/usr/bin/openssl`, fixed argv, minimal env), name/subnet constraints, atomic writes, inspection hardening deferred from 6b-1, the journal (CA transactions that recover to one consistent CA and leaf after a crash), `pipulse tls status/init/renew/new-ca/restore-ca/export-ca/enable/disable`, the renewal timer and the `openssl` package dependency. Upgrades write no `state.json` and make no CA.
- **6b-2b** (Tasks 14–20, `release:patch` → v0.6.5), visibility, still opt-in: `/run/pipulse/tls-status.json`, renewal and CA details in `/api/health` and `/api/config`, certificate expiry alerts in `packages/alerts`, the Settings Certificate section (coverage lines, year in "Valid until", live refresh), and the plain-HTTP hint page on the HTTPS port (ruling R14).
- **6b-2c** (Tasks 21–27, `release:minor` → v0.7.0), HTTPS by default: `RELEASE_DEFAULT` flips to `refuse`, `setup.sh` migration (fresh → `https`, upgrade → `legacy-http` even if `/etc/pipulse/tls` was deleted, via the `tls-installed` marker), the installer's interactive subnet prompt, the Docker sidecar and compose hardening (the server never mounts the `tls-ca` volume), docs.

Invariants the plan sets: the CA key (`ca/ca.key`, `0600` in a `0700` root-only directory) is never readable by the long-running server, native or Docker; a native install keeps generated material only in `/etc/pipulse/tls` (R15, the renew unit's sandbox writes nowhere else); nothing issues on an unsynced clock (`renew` records `waiting-clock`); `PIPULSE_TLS=off` overrides everything; a certificate problem never stops collection, alerts or notifications; the fingerprint is shown only over local channels and `export-ca` prints the fingerprint of the exact bytes it exports. ## Working conventions established so far

- Node.js >=22.13.0 required — storage uses the built-in `node:sqlite` (`DatabaseSync`), not `better-sqlite3` (dropped after npm/cli#9450 made it impossible to selectively allow its install script under this machine's `ignore-scripts=true`).
- Packages build in dependency order: storage → collector → alerts → notify → tls → api → web (no TS project references / `tsc -b` wired up — plain sequential `npm run build --workspace=...` calls in the root `package.json`).
- Keep core logic decoupled from specific libraries (Fastify, Preact, node:sqlite) behind small interfaces — see "Future-proofing & extensibility" in `docs/PLAN.md` for the reasoning (stable versioned `CollectorPlugin` interface, thin adapters, contract tests).
- Every phase's exit criterion includes tests passing in CI, not just Phase 0.
- The target Pi (the Pi-hole box, hostname `Io`) is a **Raspberry Pi 2 Model B Rev 1.1**, **armv7l** (32-bit) and its system Node at `/usr/bin/node` is NodeSource 16.x — too old for `node:sqlite`. Phase 1 was verified with a newer per-user Node (nvm). Phase 6's systemd unit must either upgrade the system Node or point `ExecStart` at a Node >=22.13; stick to Node 22 LTS for armv7l builds.
- PiPulse's default port is **8889**, so it installs next to legacy **RPi-Monitor on 8888** (still on the Pi until cutover, Phase 7) without a clash. RPi-Monitor answers 200 to every path, so the installer's health check requires PiPulse's own `{"status":"ok"}` body, not just a 200. The Pi has **ufw active with default DROP**: any new port needs an allow rule (`sudo ufw allow from 192.168.1.0/24 to any port <port> proto tcp`), otherwise remote clients time out rather than get refused. Phase 6's install script should detect active ufw and warn if the port isn't allowed.
- `npm ci` on the Pi warns that esbuild's postinstall is blocked by `ignore-scripts` — harmless (esbuild is only a dev/build tool via tsx/Vite; the server never loads it). Don't approve it unless a build actually fails.
- The dev machine has `ignore-scripts=true`, which also makes npm skip `pre*`/`post*` lifecycle hooks. So `npm test` runs `npm run build` explicitly instead of via a `pretest` hook — don't reintroduce pre/post hooks for anything that must run.
- The `vcgencmd` plugins (`cpu_voltage`, `throttled`) need the PiPulse process to open the firmware interface: the service user must be in the **`video` group**, and a Docker container needs `--device /dev/vchiq`. Phase 6's systemd unit/install script and Dockerfile must set this up. Without it, each plugin logs one "vcgencmd can't reach the firmware" error and its tile stays on "No readings yet". **Still unconfirmed on the Pi:** that vcgencmd run by a non-`video` user writes stderr matching `vchiq|VCHI|permission denied` (the check in `packages/collector/src/vcgencmd.ts`); if it doesn't, the error is logged on every poll instead of once.
- Every request goes through the one auth hook in `packages/api/src/auth-routes.ts`; never check auth inside a route. The sign-in form posts with plain `fetch` so a wrong password's `401` isn't mistaken for an expired session (everything else goes through `apiFetch` in `packages/web/src/api.ts`).
- Saved settings are read live (`retentionSource()`), never cached at startup, so the standalone collector and housekeeping see changes without a restart.
- `PIPULSE_TRUST_PROXY` stays out until a reverse proxy actually fronts PiPulse (see "Future: behind a reverse proxy" in `docs/PLAN.md`): trusting `X-Forwarded-*` without one lets any client spoof them.
- Durations (alert `for`/`clearAfter`/`noReadingFor` and `PIPULSE_RETENTION_*`) share one parser in `packages/storage/src/rollup.ts`: `s`, `min`, `h`, `d`, `w`, `y`, `forever` — a bare `m` is rejected (minutes or months?).
- Alert rules come from three layers merged by `id` — built-ins, `PIPULSE_ALERTS_FILE`, then rules saved from the browser (settings key `alerts.rules`) — read live by `createRuleSource()` on every check. A bad file stops startup; a bad saved rule is skipped and shown as 'Not in force'. Rules are always data validated by `parseRuleEntry`, never code.
- Migrations are keyed by `PRAGMA user_version`, so editing an unshipped migration leaves any dev/test database already at that version stale (Phase 4 hit this: a DB made from an earlier migration 3 lacked `rollup_progress` and housekeeping failed). Recreate test databases after changing a migration; once a migration is on `main`, never edit it — append a new one.
- Migration 6 (`alerts.acknowledged_at`, `alerts.rule_hash`) ships with 5b-2 (PR #20); once that is on `main`, never edit it — the next schema change is migration 7.
- Packaging scripts in `packaging/` are POSIX `sh` (checked by `shellcheck` with the repo's `.shellcheckrc`) and tested by `packaging/test/*.test.sh`, which run as root in Debian containers — locally through Colima (`docker` must be running; `docker buildx` comes from Homebrew's `docker-buildx`). Tests fetch Node for the container's own CPU (arm64 on the Mac, amd64 in CI). Colima only shares the home folder, so bind-mount test files from inside the repo, not `/tmp`.
- `.deb`s are built with `dpkg-deb -Zxz`: the release runs on Ubuntu, whose default zstd can't be unpacked by dpkg before 1.21.18 (Raspberry Pi OS 11), and the packaging tests run on bookworm, which reads both — so `deb.test.sh` checks the members.
- Never bump versions in `package.json` (they stay `0.0.0`): a release stamps `version.json` into what it ships. A new Node major needs its end date in `NODE_SUPPORT_ENDS` (`packages/api/src/version.ts`); 32-bit (`armhf`) stays on Node 22, the last line with 32-bit ARM builds.
- After adding any JavaScript file, run the repo-wide `npm run lint` (Phase 6's Docker health check failed CI for want of Node globals).
- `packages/tls` has no `@pipulse/*` dependencies and builds before `api`.
- `/health` (bare liveness) and `/api/health` (public, enums only) are distinct — don't merge them.
- HSTS stays opt-in: it ignores ports and `Io` serves Pi-hole/RPi-Monitor over HTTP.
- Test certificates are committed under `packages/tls/test/fixtures` (regenerate with `make-fixtures.sh`, OpenSSL 3; on the Mac that is Homebrew's `/opt/homebrew/opt/openssl@3/bin`).
- Notifications: webhooks come only from `PIPULSE_NOTIFY_FILE` (never the API); URLs beyond the host and headers are never logged, served or shown; the outbox is migration 7.
- The operator's Apprise sits behind a homelab HTTPS proxy whose certificate comes from a private CA: Node needs `NODE_EXTRA_CA_CERTS=<ca.pem>`, so Phase 6's systemd unit and Dockerfile must let the operator set it (e.g. an `EnvironmentFile`).
- When running an exit criterion on the Pi, capture the relevant API state (e.g. `/api/alerts?state=all`) before deleting the scratch database, so anything unexpected can be explained afterwards.
- To test history at scale, seed a database directly in its steady state (raw 2d, 1m 14d, 1h 1y, 1d) with the current `openDb` rather than generating a year of raw data; copy it to the Pi with `scp` using **absolute** local paths, and delete any old `-wal`/`-shm` files before replacing a database file.
- Storage tests pin `TZ=Europe/Madrid` (`packages/storage/vitest.config.ts`) so daily rollups are tested across real DST days.
- Vitest 5 ignores `vitest.workspace.ts`; the root `vitest.config.ts` uses `test.projects: ['packages/*']` so each package's own config applies.
- Renovate (`renovate.json`): majors never open PRs by themselves — they wait on the Dependency Dashboard (issue #27) for approval; Node in the workflows/containers and `@types/node` stay on 22 (armhf ships Node 22; the Dockerfile's Node 24 is 64-bit only and is not pinned); patch/minor/digest updates automerge, runtime ones carry `release:patch`. Mend's Renovate app was in silent mode at first and its first real scan opened four major PRs that were closed unmerged (2026-09-30).
- Commit messages here have included a `Co-Authored-By`/`Claude-Session` trailer from whichever Claude surface made the change — keep doing that if your environment sets one.
- `pipulse tls` never sources `pipulse.env` (it runs as root; `settingsEnv` reads it as data and refuses an unreadable file unless the environment already has `PIPULSE_TLS`).
- Issuance runs only `/usr/bin/openssl` through `execFile` with a fixed argv; tests find an OpenSSL through `packages/tls/test/openssl.ts` (`PIPULSE_TEST_OPENSSL`, else Homebrew's `openssl@3`). Before issuing, every command calls `opensslVersion()`.
- `tls.checkServerIdentity` can't match IPv6 literals (Node 22/24): use `X509Certificate.checkIP` for an IP identity.
- Every write under the TLS folders goes through `writeAtomic`; look paths up with `pathExists` (false only for ENOENT), never `existsSync`, wherever "absent" would skip a step or let a second CA be made.
- Certificate alerts use the pseudo-metric `certificate` (`CERTIFICATE_METRIC`); `ruleHash` only appends fields (`certExpiresWithin`, `certExpired` when present), so existing rules' hashes never change.
- Anything read from `/run/pipulse/tls-status.json` is untrusted (the service user writes it, root reads it): validate it, and run text through `printable()` before printing.
- `RELEASE_DEFAULT` in `packages/tls/src/config.ts` is the one release-default switch (still `'http'`; Task 21 flips it).
- Commands that change the CA or the mode run under `withLock` and call `recover()` only where they may write; read-only commands (`status`, `export-ca`) never lock, recover or clean temp files.
- Packaging tests run as root inside a Debian container, never on the Mac: copy the repo into the container (`rsync` without `node_modules`) rather than bind-mounting it read-write, or the container's `npm ci` replaces your host `node_modules`.

## For any coding agent (Claude Code, OpenCode, others)

`AGENTS.md` is a symlink to this file, so every agent that reads either name sees the same rules. Nothing below depends on Claude-only features.

**Building from a plan**

- Plans live in `docs/superpowers/plans/`, specs in `docs/superpowers/specs/`. Where a plan and its spec differ, the plan wins for the parts it lists under "Spec corrections needed" (6b-2: `docs/superpowers/plans/2026-09-30-https-6b2.md`). Ignore its "REQUIRED SUB-SKILL" line if your tool has no such skills; the steps stand alone.
- Do one task at a time, in order. Read the task's own steps, `Global Constraints`, `Review Focus` and `File Structure` first, plus any earlier task whose names it uses (types, file names, constants); don't load the whole plan. Tasks are test-first: write the failing test, see it fail, make it pass, commit.
- The code inside a plan is a reviewed draft, never run. If a test or the compiler disagrees with it, the test wins: fix the code, keep the task's intent, and note the change in the commit message.
- 6b-2 gates: Task 1 (the `openssl` spike) decides whether later tasks stand or the DER-encoder fallback (D4) is needed; don't start Task 2 before it is recorded in the plan. D2 stays off until a person records a Chrome/Firefox/Safari result. Tasks 13, 20 and 27 are manual exit criteria on the Pi (`Io`) or a Docker host; an agent writes the checklist and stops.
- Before a PR: `npm test` (it builds first), `npm run lint`, `npm run format`; for `packaging/` also `shellcheck` and the `packaging/test/*.test.sh` suite. Every PR needs green CI, and a release label (`release:patch|minor`) only when it should ship.

**Working with the Pi and the user's machines**

- The Pi (`Io`) uses password SSH only, so an agent can't log in. Give the person exact commands to run, and read results back through `curl` or a browser against `http://<pi>:8889`.
- Every command handed to the person uses absolute paths, never `./`: an `rsync ./ …` run from the wrong directory once copied a whole home folder to the Pi.
- Give Pi start commands as separate `export VAR=…` lines followed by one short `node …` line: a long one-line `VAR=… node …` got split when pasted over SSH, and PiPulse fell back to port 8888.
- Put built artifacts (tarballs, `.deb`s, test builds) in `~/Repositories/tarballs/<Project>/` on the Mac and `~/tarballs/<Project>/` on the Pi, outside any git repo.
- Before a scratch database is deleted after an exit-criterion run, capture its API state (e.g. `/api/alerts?state=all`); two Pi-only oddities once couldn't be explained because it was gone.
- The operator's Apprise sits behind a homelab HTTPS proxy with a private CA, so a Node process that sends to it needs `NODE_EXTRA_CA_CERTS`.

**Cost and review**

- Use the strongest available model for planning and for the risky 6b-2 code (the CA journal, certificate issuance and constraints, CA rotation) and for the final whole-branch review; a cheaper model is fine for the rest. Give reviews a fresh context that didn't write the change.
- Don't use Codex in this repo (broken, dropped by the operator).
