# PiPulse — project instructions for Claude

PiPulse is a from-scratch TypeScript rewrite of [RPi-Monitor](https://github.com/RPi-Monitor/RPi-Monitor). This file is read automatically by Claude Code (CLI) when working in this repo, so it doesn't matter whether work continues here via Claude Code or via Cowork/claude.ai — both should end up looking at the same two documents below.

## Where the plan lives

- **`README.md`** — current status, tech stack with pinned versions, the quick install and the roadmap table (which phase is done, which is next). The long how-to pages live in `docs/` (`install.md`, `https.md`, `docker.md`, `configuration.md`, `alerts.md`, `api.md`, `architecture.md`, `development.md`); keep the README short and put new user documentation there.
- **`docs/PLAN.md`** — the full modernization plan: legacy architecture review, every architecture decision and why, data/storage schema, API/frontend design, deployment plan, feature-parity matrix, the phase-by-phase build plan with exit criteria, testing strategy, security considerations, and future-proofing notes. Read this before starting a new phase.

Read both before proposing what to build next — `README.md`'s roadmap table is the quick status check, `docs/PLAN.md` has the reasoning and exit criteria behind each phase.

## Current status

Phase 0 (foundations) is done: npm-workspaces monorepo (`packages/storage`, `packages/collector`, `packages/api`, `packages/web`), lint (ESLint flat config), tests (Vitest), CI (GitHub Actions, Node 22.x/24.x matrix).

Phase 1 (collector core) is done (PR #1): `packages/collector` has the versioned `CollectorPlugin` interface with runtime `validatePlugin()` checks and a contract suite run against every built-in plugin; six built-in plugins (`cpu_load`, `memory_used`, `network_rx`, `network_tx`, `disk_used`, `cpu_temperature`); `startScheduler()` (per-plugin intervals, skips a tick while the previous read is still in flight, `stop(timeoutMs)` drains before the db closes); and a `src/main.ts` daemon (`PIPULSE_DB_PATH`, clean SIGINT/SIGTERM shutdown). Exit criterion verified on the real Pi-hole Pi (armv7l): all six metrics landed at their configured 5 s / 10 s / 60 s intervals. 51 tests passing; `npm test`, `npm run build`, `npm run lint`, and `npm run format` all green.

Phase 2 (API layer) is done (PR #4): `packages/api/src/server.ts` is a single process that runs the collector scheduler and serves Fastify REST (`/api/config`, `/api/metrics/latest`, `/api/metrics/:id/history` with schema-validated `from`/`to`) plus a `/api/live` WebSocket (`snapshot` on connect, then one `sample` per reading). The scheduler's `onSample` hook publishes into an in-process `LiveFeed` (a small interface in `packages/api`, so the API never imports the scheduler directly). Config via `PIPULSE_DB_PATH`, `PIPULSE_HOST`, `PIPULSE_PORT`. Exit criterion verified from a Mac against the Pi on port 8889: `curl` and a WebSocket client both returned live data. 65 tests passing.

Phase 3 (dashboard) is done (PRs #6, #7): `packages/web` is a Preact dashboard served by the API at `/` (`@fastify/static`, `PIPULSE_WEB_DIR`). Hostname header with model/OS/kernel from `/api/config`'s `device` section and uptime from its top-level `uptimeMs` (read from `os.uptime()` on every request and advanced in the browser with `performance.now()`; deliberately not a stored boot timestamp, because the Pi has no RTC and a boot time computed before NTP syncs stays wrong by however far the clock later jumps), a Live/Reconnecting indicator that pulses per sample, and one tile per plugin (formatted value, meter where there's a ceiling, 15-minute sparkline from history + live samples). Display-only status thresholds (icon + words, never colour alone) live in `packages/web/src/now/status.ts` until Phase 5's alert engine. Staleness and history windows use the Pi's clock (`serverTime`, then pushed sample timestamps). 11 built-in plugins now, including `swap_used`, `boot_used`, `cpu_frequency`, and `cpu_voltage`/`throttled` via `vcgencmd` (the vcgencmd plugin deferred from Phase 1). Exit criterion verified by screenshot side by side with RPi-Monitor's `status.html` on the Pi: PiPulse shows everything that page does except load averages and cumulative network totals, deferred to Phase 4. 183 tests passing.

Phase 4 (history & charts) is done (PR #14): a housekeeping job (`startHousekeeping` in `packages/storage/src/rollup.ts`, run in-process every minute) rolls raw → 1m → 1h → 1d and prunes per `PIPULSE_RETENTION_*` (defaults raw 2d, 1m 14d, 1h 1y, 1d forever). Daily buckets are the server's **local** calendar days (DST-aware, built from 1m rollups), with a `rollup_progress` table (migration 3) recording where they stopped. `GET /api/metrics/:id/series` returns avg/min/max points; `resolution=auto` (`chooseResolution`) picks the finest level that is whole across the window (not yet pruned there by retention) and actually holds ≤1500 rows for that metric in it — counted with a `LIMIT 1501` index scan, not estimated from the span, so a database younger than a level's first bucket (e.g. <1 h for hourly) still gets the readings it has instead of an empty chart. `packages/web` has a hash-routed History page (`#/history?range=1h|6h|24h|7d|30d|1y`) with uPlot charts, drag-to-zoom (refetches finer data), a low–high band and gap breaks. Exit criterion verified on the Pi 2 with a seeded year-equivalent database (380k raw / 222k 1m / 96k 1h / 4k 1d rows): every range answers in under 75 ms, the 1-year page loads all ten series in ~250 ms from daily rows, and series queries seek on the primary key (no raw-table scan). 273 tests passing.

Phase 5a (alerting) is done (PR #18): `packages/alerts` holds the rules (built-ins in `rules.ts`, merged by `id` with the operator's `PIPULSE_ALERTS_FILE`; one condition per rule — `atLeast`/`atMost`/`bitsSet`/`noReadingFor` — with `for`/`clearAfter` durations; an invalid file stops startup), a pure raise/clear decision over covered windows of readings (`evaluate.ts`), a SQLite adapter (`store.ts`, the `alerts` table is migration 4) and a 15 s engine run in the server that survives restarts and clock jumps and logs a failed check instead of crashing. The API serves `GET /api/alerts`, `rules` in `/api/config`, open `alerts` in the WebSocket snapshot and an `alert` message per raise/clear. The dashboard colours tiles from the same rules (replacing the display-only thresholds), shows open alerts live on tiles, and has an Alerts page (open, last 30 days, rules in force) with a per-severity badge in the nav. A window only counts as evidence if readings reach both ends and no more than two polls are missed in a row anywhere in it; silence rules fall back to the newest rollup bucket once the raw reading is pruned, so `noReadingFor` isn't bound by raw retention. Exit criterion verified on the Pi 2 (port 8889, test rules file): a `yes`-loop CPU breach opened `test_busy` live on the Alerts page and badge with no reload, the same alert (one row) survived a server restart, it cleared ~1 min after `pkill yes` (`clearedBy: condition`) and moved to Recent live, a 30 s `noReadingFor` rule on the 60 s `disk_used` opened and cleared every minute, `/api/alerts` answered in 26–40 ms, and no `alert rule … failed` lines were logged. 381 tests passing.

Phase 5b-1 (sign-in, settings, retention editor) is done (spec `docs/superpowers/specs/2026-09-23-settings-auth-design.md`, plan `docs/superpowers/plans/2026-09-23-settings-auth.md`). `packages/api/src/auth.ts` (no Fastify types) holds the scrypt hash file (`PIPULSE_ADMIN_PASSWORD_HASH_FILE`, made by `node packages/api/dist/hash-password.js`; unset = read-only), in-memory sessions (`pipulse_session` cookie, `HttpOnly`, `SameSite=Strict`, 7 days from last use) and the sign-in limit (5 failures per IP per 15 min). One `onRequest` hook in `auth-routes.ts` decides every request: writes need a session (and a same-host `Origin`), reads only with `PIPULSE_PROTECT_READS=true` (the WebSocket then closes with `4401`). Storage has the `settings` table (migration 5) and `retentionSource()`: environment › saved › default, re-read on every housekeeping run and `/series` request, so a saved change applies within a minute without a restart; `validateRetention` keeps levels in order and raw retention ≥ the longest alert look-back. `PUT /api/settings` answers `409` until a deleting change is confirmed; housekeeping runs `VACUUM` after large deletes (≥ 25 % free of a > 8 MB file, disk room for a copy, at most daily). The dashboard has a Settings page (preview, confirm checkbox, locked env fields, storage figures), a sign-in form, a full-page sign-in gate under read protection, and Sign out. The auth hook decides on the matched route (never the raw URL, which percent-encoding or an absolute-form target can disguise), and a preview counts only rows the change itself deletes. Exit criterion verified on the Pi 2 (port 8889, a seeded 21.6 MB database with two days of raw readings): without a hash file the Settings page was read-only and `PUT /api/settings` (and `/%61pi/settings`) answered `403`; with one, unauthenticated writes answered `401`, the `hash-password` prompt hid the typing, and cutting raw retention from `2d` to `1h` in the browser (preview, confirm, Save) deleted ~220k raw rows within a minute and logged `vacuum: 21.6 MB → 4.0 MB in 1.2 s` (requests waited a few seconds during the delete and vacuum); the saved value survived a restart, which signed the browser out; with `PIPULSE_PROTECT_READS=true` every `/api` read answered `401`, the WebSocket closed with `4401`, a signed-out browser saw only the sign-in form, and after signing in the dashboard went Live. 481 tests passing.

Phase 5b-2 (alert rules in the browser) is done (PR #20; spec `docs/superpowers/specs/2026-09-24-alert-rules-editor-design.md`, plan `docs/superpowers/plans/2026-09-24-alert-rules-editor.md`). Rules come from three layers merged by `id` — built-ins, `PIPULSE_ALERTS_FILE`, then rules saved from the browser (settings key `alerts.rules`) — via `createRuleSource()` in `packages/alerts/src/source.ts`, read live on every 15 s check. API: `GET /api/alerts/rules`, `POST /api/alerts/rules` (create; `409` if the id is taken), `PUT`/`DELETE /api/alerts/rules/:id`, `POST /api/alerts/:id/acknowledge`; `/api/live` sends `rules` after an edit (and in its snapshot) and `acknowledged` after an acknowledgement. The Alerts page has the rules editor (Edit / Disable / Enable / Revert / Delete, inline form with server errors under their fields) and Acknowledge buttons. `swap_heavy` now watches a `swap_io` plugin (pages/s swapped in+out from `/proc/vmstat`, History only) at ≥ 250 pages/s for 10 min instead of swap fullness; `swap_full` still watches `swap_used` ≥ 95 %. Phase 6b-1 (TLS core) is done (PR #35, released as v0.6.3 on 2026-09-30). `packages/tls` reads the settings (`PIPULSE_TLS`, `_CERT`/`_KEY`/`_CA`, `_NAMES`, `_REQUIRE_VALID_CERT`, `_HSTS`, `_CLOCK`, `_TIMESYNC_DIR`; release default HTTP), loads and classifies an operator certificate (refused cases stop startup with one line naming the setting, e.g. `PIPULSE_TLS_CERT/PIPULSE_TLS_KEY: …` or `PIPULSE_TLS_CA: certificate N can't be parsed`; incomplete chain, untrusted top or a missing name only degrade; `notBefore`/`notAfter` are the served chain's window, so an expired intermediate reads as `expired`, never a refusal by itself), checks the clock, and reloads changed files every 60 s after two stable polls (signature includes mode/owner, context fingerprint covers key + chain), keeping the old context on a bad or worse replacement and holding replacements to startup's validity rules; a refused replacement is retried every 10 min while its files stay the same, and the reloader takes the file signature read before the startup load. `PIPULSE_TLS_NAMES` is checked against SANs only, never the subject CN. `/api/health` reports `monitoring`, `transport`, top-level `reasons` and `certificate` (enums only; an HTTP install with a password now says `degraded`/`http-with-sign-in`, release-noted); `/api/config` has `tls`; Settings has a Certificate section. TLS CLI review (2026-10-13, fresh-context Opus review of `packages/tls`'s commands, no release label): `init --mode auto` over an operator certificate made no folder before writing `state.json` (a fresh install died, an upgrade fell back with a wrong message) and ran unlocked; `ensureStateDirs` makes the folder (never re-owning one the operator pointed `PIPULSE_TLS_DIR` at, such as `/etc/ssl`) and `init --mode` always locks. A synced clock that had jumped ahead and come back made `renew` issue a leaf dated in the future and then call the clock "unsynced" forever (`readClock` no longer takes `notBefore`; `renewDue` and `init` replace a leaf whose start is in the future). `new-ca --name` now reaches the leaf (`leafNames` adds the CA's dotted names) and a rotation keeps the CA's names like it keeps its subnets (`--name none` drops them). `export-ca --out` writes as the `sudo` caller (`asCaller` drops uid, gid and groups), end of input at a prompt answers no, a damaged `state.json` is named and replaced by `enable`/`disable`, `setup.sh` writes its fallback `state.json` atomically, `enable` over an operator certificate that only fails verification (exit 2) warns and stays on HTTPS like the installer, a failed backup prune after `new-ca` is a warning, `status` no longer says HTTPS is ready without a CA, and the health and clock waits use the monotonic clock (`Context.monotonic`). The lock's wait deadline is on the monotonic clock since 2026-10-13, and `renew` got a clock-anchor check against a clock that runs far ahead (see "Renew clock anchor", below).

Mutation runs on the highest-stakes code (2026-10-13, `npm run mutate`, whole runs took about 12 minutes; tests only, no release label): `host.ts`, `auth.ts`, `constraints.ts`, `inspect.ts`, `reload.ts`, the lock's breaker turns and wait loop, and `issue.ts` scored 68–90 % with 359 survivors; new `test/*.mutation.test.ts` files (and four cases in `host.test.ts`) bring them to 94.6–100 % with 70 survivors, nearly all judged equivalent by reading (string fallbacks that fail a later check, a `readFileSync` encoding that `JSON.parse` coerces, a loop bound a typed array ignores). Known unkillable: the `system` public-roots flag in `inspect.ts` (needs a chain to a real public root), and four `inspect.ts` mutants that loop forever on two cross-certified anchors and die only by timeout (run them on an idle machine). Run mutation on a copy of the repo (`cp -cR`), never in the working tree, and give each parallel agent its own scratch script names.

Renew clock anchor (2026-10-13, no release label): `renew` keeps a second opinion on the wall clock (`packages/tls/src/ca/clock-anchor.ts`). `clock-anchor.json` in the TLS folder holds the wall clock minus the time since boot (`os.uptime()`, which clock steps do not move) and the boot id. A run that finds that offset more than 10 minutes larger than the last run's does not issue (unless `--force`): it records `waiting-clock` ("the clock stepped ahead by … since the last check") and remembers the step, which is believed once it has held for 30 minutes. A step back is followed, a new boot starts afresh, `init`/`new-ca` are unaffected, and a context without `uptime`/`bootId` (tests, other callers) skips the check. Docs: `docs/https.md`.

TLS health review (2026-10-13, fresh-context Opus review of `clock.ts`, `health-check.ts`, `runtime-status.ts` and `sidecar.ts`, no release label): the health check no longer goes through `HTTP(S)_PROXY` (Node 24's `NODE_USE_ENV_PROXY` sent even the loopback probe to the proxy, so the Docker image of an operator with a proxy was unhealthy for good), uses `http.request` with a fresh agent instead of `fetch`, probes a wildcard-only certificate as `pipulse.<domain>` (the literal `*.example.com` Host got a `421` under `PIPULSE_ALLOWED_HOSTS`, which rolled back a good upgrade; a `421` now says to set `PIPULSE_TLS_NAMES`), trusts exactly `PIPULSE_TLS_CA` or Node's bundled roots (`NODE_EXTRA_CA_CERTS`, set for webhooks, made a private-CA operator certificate look trusted), and while a `new-ca`/`restore-ca` leaf written in the last 10 minutes is waiting for the server's reload (running server still serves another certificate) reports healthy with that message instead of a verification failure. `sidecar` stops on SIGTERM/SIGINT (PID 1 had no handler, so `docker stop` waited out its timeout and SIGKILLed it, possibly mid-renewal); with `PIPULSE_TLS=off` a failed init no longer keeps the server from starting; a state.json that is readable but invalid is a warning, not a refusal, when `PIPULSE_TLS=on|off` decides the mode; `/api/health` counts a renewal that keeps waiting for the clock as `renewal-failing` once the leaf is within 30 days of expiry; and the API no longer reads a future-dated leaf as an unsynced clock (the same rule `readClock` lost in the CLI review). Not changed since: the lock's wait deadline moved to the monotonic clock on 2026-10-13, and `renew` got a clock-anchor check ("Renew clock anchor", above).

- `npm ci` on the Pi warns that esbuild's postinstall is blocked by `ignore-scripts` — harmless (esbuild is only a dev/build tool via tsx/Vite; the server never loads it). Don't approve it unless a build actually fails.
- The dev machine has `ignore-scripts=true`, which also makes npm skip `pre*`/`post*` lifecycle hooks. So `npm test` runs `npm run build` explicitly instead of via a `pretest` hook — don't reintroduce pre/post hooks for anything that must run.

Phase 6's systemd unit/install script and Dockerfile must set this up. - Startup is `loadConfig` (pure: it reads and validates, creates nothing) then `startServer` (the wiring, returning a handle with an idempotent `stop()`); `packages/api/src/server.ts` is only the entry. A new setting is read in `config.ts`; a new part that starts or stops goes in `runtime.ts`'s start and `stopParts` together. Tests that start the server use `startServer(config, { plugins, device })` with a fake plugin for every built-in id (the built-in rules name them all).

Put a new module in its area's folder, and import across areas only from `core/` (and the shell's small modules `router.ts`, `build.ts`, `sign-in.tsx`, never `app.tsx`/`main.tsx`); `test/module-layering.test.ts` enforces it. `StatusIcon`, which every page shows, is in `core/status-icon.tsx`.

- Saved settings are read live (`retentionSource()`), never cached at startup, so the standalone collector and housekeeping see changes without a restart.
- `PIPULSE_TRUST_PROXY` stays out until a reverse proxy actually fronts PiPulse (see "Future: behind a reverse proxy" in `docs/PLAN.md`): trusting `X-Forwarded-*` without one lets any client spoof them.

- Certificate alerts use the pseudo-metric `certificate` (`CERTIFICATE_METRIC`); `ruleHash` only appends fields (`certExpiresWithin`, `certExpired` when present), so existing rules' hashes never change.
- Anything read from `/run/pipulse/tls-status.json` is untrusted (the service user writes it, root reads it): validate it, and run text through `printable()` before printing.
- `RELEASE_DEFAULT` in `packages/tls/src/settings/config.ts` is the one release-default switch (`'refuse'` since v0.7.0).
- Commands that change the CA or the mode run under `withLock` and call `recover()` only where they may write; read-only commands (`status`, `export-ca`) never lock, recover or clean temp files.
- `e2e/` is standalone: its own `package.json`/lockfile, never in the root `workspaces`, `build` or `test` (`npm run test:e2e` runs it; it needs the root build first, since a clean checkout has no `dist/`). No production code reads `PIPULSE_E2E_*`. Specs use no fixed sleeps and role/label locators; browsers install only by an explicit `npx --prefix e2e playwright install chromium`, never from a lifecycle script. Nothing in it touches `Io`.
- The e2e harness swaps the server's plugins through a module hook: a new built-in plugin needs a default in `e2e/src/harness/readings.ts`, and the specs keep retries at 0.
- Packaging tests run as root inside a Debian container, never on the Mac: copy the repo into the container (`rsync` without `node_modules`) rather than bind-mounting it read-write, or the container's `npm ci` replaces your host `node_modules`.

- Fresh installs are HTTPS; `setup.sh` decides the mode only when `state.json` is absent (`decideInitialMode`) and never switches an upgrade. The server writes `tls-installed` next to the database after serving HTTPS, and `npm run dev` defaults to `PIPULSE_TLS=off`.
- The Docker `pipulse` uid/gid is pinned to 999 (the compose `tmpfs` and `group_add` use it), and the sidecar's health stays readiness-only: never make a certificate problem fail `sidecar-health`.
- `PIPULSE_TLS=off` must be honoured by every path that would make a CA (`init --mode auto`, the sidecar); only an explicit manual `pipulse tls init` still issues.
- `setup.sh` never replaces a masked unit file and never re-enables a unit an operator disabled after the first time (the renewal timer's marker is `/etc/pipulse/.renew-timer-enabled`).

## For any coding agent (Claude Code, OpenCode, others)

`AGENTS.md` is a symlink to this file, so every agent that reads either name sees the same rules. Nothing below depends on Claude-only features.

**Building from a plan**

- Plans live in `docs/superpowers/plans/`, specs in `docs/superpowers/specs/`. Where a plan and its spec differ, the plan wins for the parts it lists under "Spec corrections needed" (6b-2: `docs/superpowers/plans/2026-09-30-https-6b2.md`). Ignore its "REQUIRED SUB-SKILL" line if your tool has no such skills; the steps stand alone.
- Do one task at a time, in order. Read the task's own steps, `Global Constraints`, `Review Focus` and `File Structure` first, plus any earlier task whose names it uses (types, file names, constants); don't load the whole plan. Tasks are test-first: write the failing test, see it fail, make it pass, commit.
- The code inside a plan is a reviewed draft, never run. If a test or the compiler disagrees with it, the test wins: fix the code, keep the task's intent, and note the change in the commit message.
- 6b-2 gates: Task 1 (the `openssl` spike) decides whether later tasks stand or the DER-encoder fallback (D4) is needed; don't start Task 2 before it is recorded in the plan. D2 stays off until a person records a Chrome/Firefox/Safari result. Tasks 13, 20 and 27 are manual exit criteria on the Pi (`Io`) or a Docker host; an agent writes the checklist and stops.
- Before a PR: `npm test` (it builds first), `npm run lint`, `npm run format`; for `packaging/` also `shellcheck` and the `packaging/test/*.test.sh` suite. Every PR needs green CI, and a release label (`release:patch|minor`) only when it should ship.

**Working with the Pi and the user's machines**

- The Pi (`Io`) uses password SSH only, so an agent can't log in. Give the person exact commands to run, and read results back through `curl` or a browser against `http://<pi>:8889`.
- Every command handed to the person uses absolute paths, never `./`: an `rsync ./ …` run from the wrong directory once copied a whole home folder to the Pi.
- Give Pi start commands as separate `export VAR=…` lines followed by one short `node …` line: a long one-line `VAR=… node …` got split when pasted over SSH, and PiPulse fell back to port 8888.
- Put built artifacts (tarballs, `.deb`s, test builds) in `~/Repositories/tarballs/<Project>/` on the Mac and `~/tarballs/<Project>/` on the Pi, outside any git repo.
- Before a scratch database is deleted after an exit-criterion run, capture its API state (e.g. `/api/alerts?state=all`); two Pi-only oddities once couldn't be explained because it was gone.
- The operator's Apprise sits behind a homelab HTTPS proxy with a private CA, so a Node process that sends to it needs `NODE_EXTRA_CA_CERTS`.

**Cost and review**

- Use the strongest available model for planning and for the risky 6b-2 code (the CA journal, certificate issuance and constraints, CA rotation) and for the final whole-branch review; a cheaper model is fine for the rest. Give reviews a fresh context that didn't write the change.
- Don't use Codex in this repo (broken, dropped by the operator).
