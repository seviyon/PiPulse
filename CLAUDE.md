# PiPulse — project instructions for Claude

PiPulse is a from-scratch TypeScript rewrite of [RPi-Monitor](https://github.com/RPi-Monitor/RPi-Monitor). This file is read automatically by Claude Code (CLI) when working in this repo, so it doesn't matter whether work continues here via Claude Code or via Cowork/claude.ai — both should end up looking at the same two documents below.

## Where the plan lives

- **`README.md`** — current status, tech stack with pinned versions, getting-started commands, and the roadmap table (which phase is done, which is next).
- **`docs/PLAN.md`** — the full modernization plan: legacy architecture review, every architecture decision and why, data/storage schema, API/frontend design, deployment plan, feature-parity matrix, the phase-by-phase build plan with exit criteria, testing strategy, security considerations, and future-proofing notes. Read this before starting a new phase.

Read both before proposing what to build next — `README.md`'s roadmap table is the quick status check, `docs/PLAN.md` has the reasoning and exit criteria behind each phase.

## Current status

Phase 0 (foundations) is done: npm-workspaces monorepo (`packages/storage`, `packages/collector`, `packages/api`, `packages/web`), lint (ESLint flat config), tests (Vitest), CI (GitHub Actions, Node 22.x/24.x matrix).

Phase 1 (collector core) is done (PR #1): `packages/collector` has the versioned `CollectorPlugin` interface with runtime `validatePlugin()` checks and a contract suite run against every built-in plugin; six built-in plugins (`cpu_load`, `memory_used`, `network_rx`, `network_tx`, `disk_used`, `cpu_temperature`); `startScheduler()` (per-plugin intervals, skips a tick while the previous read is still in flight, `stop(timeoutMs)` drains before the db closes); and a `src/main.ts` daemon (`PIPULSE_DB_PATH`, clean SIGINT/SIGTERM shutdown). Exit criterion verified on the real Pi-hole Pi (armv7l): all six metrics landed at their configured 5 s / 10 s / 60 s intervals. 51 tests passing; `npm test`, `npm run build`, `npm run lint`, and `npm run format` all green.

Phase 2 (API layer) is done (PR #4): `packages/api/src/server.ts` is a single process that runs the collector scheduler and serves Fastify REST (`/api/config`, `/api/metrics/latest`, `/api/metrics/:id/history` with schema-validated `from`/`to`) plus a `/api/live` WebSocket (`snapshot` on connect, then one `sample` per reading). The scheduler's `onSample` hook publishes into an in-process `LiveFeed` (a small interface in `packages/api`, so the API never imports the scheduler directly). Config via `PIPULSE_DB_PATH`, `PIPULSE_HOST`, `PIPULSE_PORT`. Exit criterion verified from a Mac against the Pi on port 8889: `curl` and a WebSocket client both returned live data. 65 tests passing.

Phase 3 (dashboard) is done (PRs #6, #7): `packages/web` is a Preact dashboard served by the API at `/` (`@fastify/static`, `PIPULSE_WEB_DIR`). Hostname header with model/OS/kernel from `/api/config`'s `device` section and uptime from its top-level `uptimeMs` (read from `os.uptime()` on every request and advanced in the browser with `performance.now()`; deliberately not a stored boot timestamp, because the Pi has no RTC and a boot time computed before NTP syncs stays wrong by however far the clock later jumps), a Live/Reconnecting indicator that pulses per sample, and one tile per plugin (formatted value, meter where there's a ceiling, 15-minute sparkline from history + live samples). Display-only status thresholds (icon + words, never colour alone) live in `packages/web/src/status.ts` until Phase 5's alert engine. Staleness and history windows use the Pi's clock (`serverTime`, then pushed sample timestamps). 11 built-in plugins now, including `swap_used`, `boot_used`, `cpu_frequency`, and `cpu_voltage`/`throttled` via `vcgencmd` (the vcgencmd plugin deferred from Phase 1). Exit criterion verified by screenshot side by side with RPi-Monitor's `status.html` on the Pi: PiPulse shows everything that page does except load averages and cumulative network totals, deferred to Phase 4. 183 tests passing.

Phase 4 (history & charts) is done (PR #14): a housekeeping job (`startHousekeeping` in `packages/storage/src/rollup.ts`, run in-process every minute) rolls raw → 1m → 1h → 1d and prunes per `PIPULSE_RETENTION_*` (defaults raw 2d, 1m 14d, 1h 1y, 1d forever). Daily buckets are the server's **local** calendar days (DST-aware, built from 1m rollups), with a `rollup_progress` table (migration 3) recording where they stopped. `GET /api/metrics/:id/series` returns avg/min/max points; `resolution=auto` (`chooseResolution`) picks the finest level that is whole across the window (not yet pruned there by retention) and actually holds ≤1500 rows for that metric in it — counted with a `LIMIT 1501` index scan, not estimated from the span, so a database younger than a level's first bucket (e.g. <1 h for hourly) still gets the readings it has instead of an empty chart. `packages/web` has a hash-routed History page (`#/history?range=1h|6h|24h|7d|30d|1y`) with uPlot charts, drag-to-zoom (refetches finer data), a low–high band and gap breaks. Exit criterion verified on the Pi 2 with a seeded year-equivalent database (380k raw / 222k 1m / 96k 1h / 4k 1d rows): every range answers in under 75 ms, the 1-year page loads all ten series in ~250 ms from daily rows, and series queries seek on the primary key (no raw-table scan). 273 tests passing.

Phase 5a (alerting) is done (PR #18): `packages/alerts` holds the rules (built-ins in `rules.ts`, merged by `id` with the operator's `PIPULSE_ALERTS_FILE`; one condition per rule — `atLeast`/`atMost`/`bitsSet`/`noReadingFor` — with `for`/`clearAfter` durations; an invalid file stops startup), a pure raise/clear decision over covered windows of readings (`evaluate.ts`), a SQLite adapter (`store.ts`, the `alerts` table is migration 4) and a 15 s engine run in the server that survives restarts and clock jumps and logs a failed check instead of crashing. The API serves `GET /api/alerts`, `rules` in `/api/config`, open `alerts` in the WebSocket snapshot and an `alert` message per raise/clear. The dashboard colours tiles from the same rules (replacing the display-only thresholds), shows open alerts live on tiles, and has an Alerts page (open, last 30 days, rules in force) with a per-severity badge in the nav. A window only counts as evidence if readings reach both ends and no more than two polls are missed in a row anywhere in it; silence rules fall back to the newest rollup bucket once the raw reading is pruned, so `noReadingFor` isn't bound by raw retention. Exit criterion verified on the Pi 2 (port 8889, test rules file): a `yes`-loop CPU breach opened `test_busy` live on the Alerts page and badge with no reload, the same alert (one row) survived a server restart, it cleared ~1 min after `pkill yes` (`clearedBy: condition`) and moved to Recent live, a 30 s `noReadingFor` rule on the 60 s `disk_used` opened and cleared every minute, `/api/alerts` answered in 26–40 ms, and no `alert rule … failed` lines were logged. 381 tests passing.

Phase 5b-1 (sign-in, settings, retention editor) is built on branch `phase-5b-settings`, exit criterion on the Pi pending (spec `docs/superpowers/specs/2026-09-23-settings-auth-design.md`, plan `docs/superpowers/plans/2026-09-23-settings-auth.md`). `packages/api/src/auth.ts` (no Fastify types) holds the scrypt hash file (`PIPULSE_ADMIN_PASSWORD_HASH_FILE`, made by `node packages/api/dist/hash-password.js`; unset = read-only), in-memory sessions (`pipulse_session` cookie, `HttpOnly`, `SameSite=Strict`, 7 days from last use) and the sign-in limit (5 failures per IP per 15 min). One `onRequest` hook in `auth-routes.ts` decides every request: writes need a session (and a same-host `Origin`), reads only with `PIPULSE_PROTECT_READS=true` (the WebSocket then closes with `4401`). Storage has the `settings` table (migration 5) and `retentionSource()`: environment › saved › default, re-read on every housekeeping run and `/series` request, so a saved change applies within a minute without a restart; `validateRetention` keeps levels in order and raw retention ≥ the longest alert look-back. `PUT /api/settings` answers `409` until a deleting change is confirmed; housekeeping runs `VACUUM` after large deletes (≥ 25 % free of a > 8 MB file, disk room for a copy, at most daily). The dashboard has a Settings page (preview, confirm checkbox, locked env fields, storage figures), a sign-in form, a full-page sign-in gate under read protection, and Sign out. The auth hook decides on the matched route (never the raw URL, which percent-encoding or an absolute-form target can disguise), and a preview counts only rows the change itself deletes. 477 tests passing.

Next up: **Phase 5b-2 — Alert rules in the browser**: add/edit/disable rules stored in the `settings` table above the file and built-ins, acknowledging alerts, and revisiting `swap_heavy`; then 5b-3, notifications on the engine's `onChange` seam (see `docs/superpowers/specs/2026-09-23-alerting-design.md`'s "Deferred to 5b"). Revisit `swap_heavy`: on the Pi 2 swap sits at a flat 81 % (old pages parked in a small swap file, not active swapping), so the built-in ≥ 80 % rule stays open permanently there — consider a swap-in/out rate, a "Swap nearly full" wording, or a threshold that suits small swap files. Load averages and network totals (deferred from Phase 3) were resolved after Phase 4 by design rather than 1:1 port: a `load_1` plugin (`os.loadavg()`, every 30 s) charted on History only (`historyOnly` in `packages/web/src/history.ts` keeps it off the Now page) with the core count (`device.cpus` from `/api/config`) drawn as a dashed line, and an "In this range: … received, … sent" line on the Network chart rebuilt from rates as avg × `count` × poll interval (`/series` points carry `count`); 5/15-minute loads and since-boot totals are intentionally not collected — see the parity table in `docs/PLAN.md`. Still not built: Playwright end-to-end tests (the dashboard is covered by happy-dom render tests in Vitest).

## Working conventions established so far

- Node.js >=22.13.0 required — storage uses the built-in `node:sqlite` (`DatabaseSync`), not `better-sqlite3` (dropped after npm/cli#9450 made it impossible to selectively allow its install script under this machine's `ignore-scripts=true`).
- Packages build in dependency order: storage → collector → alerts → api → web (no TS project references / `tsc -b` wired up — plain sequential `npm run build --workspace=...` calls in the root `package.json`).
- Keep core logic decoupled from specific libraries (Fastify, Preact, node:sqlite) behind small interfaces — see "Future-proofing & extensibility" in `docs/PLAN.md` for the reasoning (stable versioned `CollectorPlugin` interface, thin adapters, contract tests).
- Every phase's exit criterion includes tests passing in CI, not just Phase 0.
- The target Pi (the Pi-hole box, hostname `Io`) is a **Raspberry Pi 2 Model B Rev 1.1**, **armv7l** (32-bit) and its system Node at `/usr/bin/node` is NodeSource 16.x — too old for `node:sqlite`. Phase 1 was verified with a newer per-user Node (nvm). Phase 6's systemd unit must either upgrade the system Node or point `ExecStart` at a Node >=22.13; stick to Node 22 LTS for armv7l builds.
- The Pi also runs **legacy RPi-Monitor on port 8888** until cutover (Phase 7), so run PiPulse on another port there (8889 was used for Phase 2). The Pi has **ufw active with default DROP**: any new port needs an allow rule (`sudo ufw allow from 192.168.1.0/24 to any port <port> proto tcp`), otherwise remote clients time out rather than get refused. Phase 6's install script should detect active ufw and warn if the port isn't allowed.
- `npm ci` on the Pi warns that esbuild's postinstall is blocked by `ignore-scripts` — harmless (esbuild is only a dev/build tool via tsx/Vite; the server never loads it). Don't approve it unless a build actually fails.
- The dev machine has `ignore-scripts=true`, which also makes npm skip `pre*`/`post*` lifecycle hooks. So `npm test` runs `npm run build` explicitly instead of via a `pretest` hook — don't reintroduce pre/post hooks for anything that must run.
- The `vcgencmd` plugins (`cpu_voltage`, `throttled`) need the PiPulse process to open the firmware interface: the service user must be in the **`video` group**, and a Docker container needs `--device /dev/vchiq`. Phase 6's systemd unit/install script and Dockerfile must set this up. Without it, each plugin logs one "vcgencmd can't reach the firmware" error and its tile stays on "No readings yet". **Still unconfirmed on the Pi:** that vcgencmd run by a non-`video` user writes stderr matching `vchiq|VCHI|permission denied` (the check in `packages/collector/src/vcgencmd.ts`); if it doesn't, the error is logged on every poll instead of once.
- Every request goes through the one auth hook in `packages/api/src/auth-routes.ts`; never check auth inside a route. The sign-in form posts with plain `fetch` so a wrong password's `401` isn't mistaken for an expired session (everything else goes through `apiFetch` in `packages/web/src/api.ts`).
- Saved settings are read live (`retentionSource()`), never cached at startup, so the standalone collector and housekeeping see changes without a restart.
- `PIPULSE_TRUST_PROXY` stays out until a reverse proxy actually fronts PiPulse (see "Future: behind a reverse proxy" in `docs/PLAN.md`): trusting `X-Forwarded-*` without one lets any client spoof them.
- Durations (alert `for`/`clearAfter`/`noReadingFor` and `PIPULSE_RETENTION_*`) share one parser in `packages/storage/src/rollup.ts`: `s`, `min`, `h`, `d`, `w`, `y`, `forever` — a bare `m` is rejected (minutes or months?).
- Alert rules are data from the built-ins and the operator's file only, never from the API. Anything that writes (rule editing, acknowledging) waits for 5b's authentication.
- Migrations are keyed by `PRAGMA user_version`, so editing an unshipped migration leaves any dev/test database already at that version stale (Phase 4 hit this: a DB made from an earlier migration 3 lacked `rollup_progress` and housekeeping failed). Recreate test databases after changing a migration; once a migration is on `main`, never edit it — append a new one.
- To test history at scale, seed a database directly in its steady state (raw 2d, 1m 14d, 1h 1y, 1d) with the current `openDb` rather than generating a year of raw data; copy it to the Pi with `scp` using **absolute** local paths, and delete any old `-wal`/`-shm` files before replacing a database file.
- Storage tests pin `TZ=Europe/Madrid` (`packages/storage/vitest.config.ts`) so daily rollups are tested across real DST days.
- Vitest 5 ignores `vitest.workspace.ts`; the root `vitest.config.ts` uses `test.projects: ['packages/*']` so each package's own config applies.
- Commit messages here have included a `Co-Authored-By`/`Claude-Session` trailer from whichever Claude surface made the change — keep doing that if your environment sets one.
